## 一、产品概述

### 1.1 产品名称
**IBDers** — IBD患者病程自我管理平台

### 1.2 产品定位
面向炎症性肠病（IBD，含克罗恩病和溃疡性结肠炎）患者的**病程记录与自我管理工具**，帮助患者系统化管理检验数据、用药记录、检查影像、注射排期等全病程信息，辅助医患沟通和治疗决策。

### 1.3 目标用户
- **核心用户**：确诊IBD的患者（克罗恩病、溃疡性结肠炎）
- **扩展用户**：患者家属/照护者、消化内科医生（查看患者自管数据）

### 1.4 产品背景
IBD是慢性病，患者需要终身管理。以一位典型克罗恩病患者的经历为例：

```
确诊 → 药物治疗 → 应答不佳换药 → 手术 → 术后恢复 → 多次方案调整
     → 生物制剂注射 → 定期检验复查 → 影像/内镜随访
```

这个过程中，患者面临的信息管理痛点：
- **检验报告分散**：纸质报告、PDF、医院APP，数据碎片化
- **指标趋势难追踪**：CRP、钙卫蛋白、血沉等关键指标跨年度对比困难
- **用药历史复杂**：多种药物、剂量调整、停药原因需要完整记录
- **注射排期易遗漏**：生物制剂有严格的注射时间窗口
- **医患信息不对称**：患者难以向医生清晰呈现完整病史

## 二、核心功能

### 2.1 检验数据管理

#### 2.1.1 PDF报告智能解析

**功能描述**：支持上传医院检验/检查报告PDF，通过**AI智能识别**自动提取关键数据，并对已解析过的医院格式生成解析模板（Skill），实现"越用越准"。

> **实现状态（2026-10-26）⚠️**：双引擎解析已实现，但**引擎运行在服务端**（`services/parse-worker`：Skill 模板命中 → 未命中回落 LLM/Vision 解析）；App/PC Web 端负责上传、确认与"用完即删"。Skill 模板的 `check_fn`、跨行（multiline）提取、"Skill 部分命中→AI 补全"均**未实现**；解析准确率（accuracy）字段存在但从未统计；数据来源标记在服务端为 `skill|ai|manual` 三值，但确认接口恒写 `skill`、App 端只写 `ai|manual` 两档，标记存在失真（已知偏差，待修）。

##### 解析架构：双引擎模式

```
用户上传PDF
    │
    ▼
┌──────────────────┐
│   Skill模板匹配   │ ←── 已学习的医院格式模板库
│  （优先命中）      │
└────────┬─────────┘
         │未命中
         ▼
┌──────────────────┐
│   AI智能解析引擎   │ ←── 大模型 + Vision能力
│  （通用兜底）      │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│   结构化数据输出   │
│  + 用户确认/修正   │
└────────┬─────────┘
         │首次解析成功
         ▼
┌──────────────────┐
│  自动生成/更新Skill │ ←── 沉淀为该医院的解析模板
└──────────────────┘
```

##### 引擎一：Skill模板解析（快速通道）

**核心理念**：每家医院的报告格式是固定的，首次解析后生成Skill模板，后续同类报告直接套用模板提取，速度更快、准确率更高。

**Skill模板内容**（✅ 已实现主体；`check_fn`/`multiline` 见下方注记）：
```yaml
hospital: 某三甲医院A
report_type: 血常规（五分类）
version: 1.2
last_updated: YYYY-MM-DD

# 日期提取规则（✅ 已实现 primary/fallback 双规则）
date_extraction:
  primary: '(\d{8})G\d+'  # 样本号格式
  fallback: '采集日期:\s*(\d{4})/(\d{1,2})/(\d{1,2})'

# 项目提取规则
items:
  - name: 白细胞计数
    alias: WBC
    pattern: '白细胞计数\s+([\d.]+)'
    multiline: true  # ⚠️ 字段可存储，但解析引擎暂不执行跨行逻辑
    unit: '10^9/L'
    ref_range: [3.5, 9.5]
    check_fn: 'v < 3.5 or v > 9.5'   # ❌ 未实现；异常判定实际按 ref_range 数值比较

  - name: 血红蛋白
    alias: Hb
    pattern: '血红蛋白\s+([\d.]+)'
    unit: 'g/L'
    ref_range: [130, 175]

  # ... 更多项目

# 特殊处理规则（⚠️ 仅内置 patient_id_mismatch / crp_multiline 两种硬编码规则）
special_rules:
  - filter: 'patient_id_mismatch'  # 病案号误匹配过滤
  - filter: 'crp_multiline'  # CRP跨行处理
```

**Skill模板管理**（⚠️ 部分实现）：
- 每家医院可生成多个Skill（按报告类型区分）— ✅（`hospital+reportType` 唯一键，版本 minor 递增 + `parentVersion` 版本链）
- 用户修正后自动更新Skill版本 — ✅（解析确认接口自动建/升版）
- Skill在用户间**共享**（社区贡献）— ✅（Web 端 Skill 社区：脱敏发布、评分、协作升版；App 端暂无社区 UI）
- 导出/导入Skill模板 — ✅ Web 端 JSON 导入/导出；App 端无
- 解析准确率统计 / 使用次数 — ⚠️ `usageCount` 已统计；`accuracy` 字段存在但无计算逻辑
- App 端本地 Skill 缓存 — ⚠️ 现为"只写不读"（解析确认后存本地规则用于展示计数），快路径匹配在服务端完成

##### 引擎二：AI智能解析（通用兜底）

**适用场景**：
- 首次遇到的医院报告格式（无Skill模板）
- 图片型/扫描型PDF（多模态大模型识别）
- 格式特殊的报告（非标准排版；**手写批注识别暂不支持** ❌）

**AI解析流程**（✅ 已实现，Vision 依赖多模态模型配置）：

| 步骤 | 处理方式 | 说明 |
|------|---------|------|
| 1. PDF读取 | pymupdf | 文字型PDF直接提取文本；文本不足 40 字符的页视为扫描件，3x 缩放栅格化为图像 |
| 2. 文本/图像理解 | 大语言模型（OpenAI 兼容接口，≤4 页图像送模） | 输入原始文本或图像，AI理解报告结构和内容 |
| 3. 结构化提取 | AI + 规则校验 | 输出标准化JSON（项目名/数值/单位/参考范围） |
| 4. 异常标注 | 规则引擎 | 根据参考范围自动标注 ↑/↓ |
| 5. 结果确认 | 用户交互 | 用户确认/修正提取结果，修正反馈回 Skill |

**AI Prompt设计示例**（✅ 与实现同源）：
```
你是一名医学检验报告解析助手。请从以下检验报告文本中提取所有检验项目，
返回JSON格式，包含以下字段：
- name: 项目中文名称
- value: 数值结果（浮点数）
- unit: 单位
- ref_min: 参考范围下限（如有）
- ref_max: 参考范围上限（如有）
- flag: 异常标记（↑/↓/null）

特别注意：
1. 有些报告的项目名和数值分两行显示，请识别关联
2. 过滤掉病案号、样本号等非检验数值
3. 区分">1800"这样的上限值和具体数值

报告文本：
{report_text}
```

##### 双引擎协作机制

| 场景 | 处理路径 | 速度 | 准确率 |
|------|---------|------|--------|
| 已有Skill模板 | 模板解析 → 输出 | 极快（<1s） | 极高（99%+） |
| 首次该医院报告 | AI解析 → 用户确认 → 生成Skill | 较慢（3-5s） | 高（95%+） |
| 图片型PDF | Vision AI → 用户确认 | 较慢（5-10s） | 中高（90%+） |
| Skill解析失败 | 降级到AI解析 → 更新Skill | 中等 | 高 |

> ⚠️ 上表速度/准确率为**设计目标**，当前无实测统计；AI 路径受大模型响应影响（默认超时 60s），无 <5s 保证，详见 §4.3。

**Skill自动生成/更新逻辑**（⚠️ 部分实现）：
1. 用户上传PDF，无匹配Skill → AI解析 → 用户确认 → **自动生成新Skill** ✅
2. 用户上传PDF，Skill解析成功但遗漏字段 → AI补全 → 用户确认 → **自动更新Skill版本** ❌（Skill 有命中即返回，无 AI 补全环节）
3. 用户手动修正AI/Skill解析结果 → **将修正反馈回Skill** ✅
4. 用户在不同医院检查 → 按医院（+报告类型）分键维护独立Skill ✅

**输出格式**（⚠️ 部分实现）：
- 中文项目名称（非英文缩写）✅
- 按时间排列的结构化数据表 ✅
- 异常值用 ↑↓ 标注 ✅
- 数据来源标记（Skill解析/AI解析/手动录入）⚠️ 服务端三值枚举已定义，但确认链路标记失真（见本节顶部注记）

### 2.4 病程时间线

#### 2.4.1 全病程时间线
**功能描述**：将所有病程事件整合为一条完整的时间线。

## 三、数据模型

### 3.1 核心实体

> 以下为**目标逻辑模型**；与当前代码实体的落地差异见 §3.2（V1.1 核对结论）。

```
Patient（患者）
├── basicInfo: 姓名、性别、出生日期、病案号、确诊日期、IBD类型
├── medications[]: 用药记录
├── labResults[]: 检验结果
├── examinations[]: 检查/影像记录
├── surgeries[]: 手术记录
├── injections[]: 注射记录
└── timeline[]: 病程事件时间线

Medication（用药记录）
├── drugName: 药物通用名
├── brandName: 商品名
├── category: 药物类别（JAK抑制剂/IL-23抑制剂/TNF-α抑制剂等）
├── dosage: 剂量
├── frequency: 频次
├── route: 给药方式（口服/皮下/静脉）
├── startDate: 起始日期
├── endDate: 停用日期（可为空）
├── status: 状态（在用/暂停/停用）
├── reason: 调整原因
└── adverseEvents[]: 不良反应记录

LabResult（检验结果）
├── date: 检验日期
├── hospital: 检验医院
├── items[]: 检验项目列表
│   ├── name: 项目名称（中文）
│   ├── value: 结果值
│   ├── unit: 单位
│   ├── referenceRange: 参考范围
│   └── flag: 异常标记（↑/↓/空）
└── source: 来源（skill｜ai｜manual 三值，见 §3.2）

Examination（检查记录）
├── date: 检查日期
├── type: 检查类型（CT/MRI/超声/内镜/病理）
├── bodyPart: 检查部位
├── findings: 检查所见
├── diagnosis: 诊断结论
├── score: 评分（SES-CD/Limberg/IBUS-SAS等）
├── comparison: 与前次对比
└── attachments[]: 影像/报告附件

Surgery（手术记录）
├── date: 手术日期
├── type: 手术类型
├── surgeon: 主刀医师
├── findings: 术中所见
├── procedure: 手术方式
├── resectedLength: 切除长度（cm）
├── totalLength: 器官总长度（cm）
├── anastomosis: 吻合方式
├── intraopScore: 术中评分
├── postopScore: 术后评分
└── diagram: 手术示意图

Injection（注射记录）
├── drug: 药物名称
├── plannedDate: 计划日期
├── actualDate: 实际日期
├── phase: 阶段（诱导期/维持期）
├── dose: 剂量
├── route: 给药方式（静脉/皮下）
├── weekNumber: 周次
└── notes: 备注

ParseSkill（解析模板）
├── hospital: 医院名称
├── reportType: 报告类型（血常规/肝功能/超声等）
├── version: 模板版本号
├── dateExtraction: 日期提取规则（正则）
├── items[]: 项目提取规则列表
│   ├── name: 项目中文名
│   ├── alias: 英文缩写
│   ├── pattern: 提取正则
│   ├── multiline: 是否支持跨行
│   ├── unit: 单位
│   ├── refRange: 参考范围
│   └── checkFn: 异常判断逻辑
├── specialRules[]: 特殊处理规则
├── source: 来源（AI生成/用户贡献/社区下载）
├── accuracy: 解析准确率
├── usageCount: 使用次数
├── sharedToCommunity: 是否已发布社区
└── ratings: 社区评分

SymptomDiary（症状日记）
├── date: 记录日期
├── painLevel: 腹痛程度（0-10）
├── diarrheaCount: 腹泻次数
├── stoolType: Bristol粪便量表（1-7型）
├── bloodyStool: 便血（无/少量/明显）
├── bloating: 腹胀程度（0-10）
├── fatigue: 疲劳程度（0-10）
├── nausea: 恶心（有/无）
├── mouthUlcer: 口腔溃疡（有/无）
├── jointPain: 关节痛（有/无+部位）
├── customItems[]: 自定义记录项
└── overallFeeling: 整体感受（比昨天好/一样/差）

BathroomRecord（排便记录）
├── dateTime: 排便时间
├── dailyCount: 当日第几次
├── stoolType: Bristol量表（1-7）
├── urgency: 紧迫感（有/无）
├── blood: 便血程度
├── mucus: 黏液（有/无）
└── notes: 备注

SleepStressRecord（睡眠压力记录）
├── date: 记录日期
├── sleepHours: 睡眠时长
├── sleepQuality: 睡眠质量（1-5）
├── difficultyFallingAsleep: 入睡困难（有/无）
├── nightWakes: 夜间醒来次数
├── stressLevel: 压力水平（1-10）
└── stressSource: 压力来源

FlareAssessment（发作评估）
├── date: 评估日期
├── level: 预警级别（🟢正常/🟡关注/🔴警告）
├── triggerFactors[]: 触发因素
├── symptomSummary: 症状摘要
├── recommendation: 建议措施
└── aiConfidence: AI判断置信度
```

### 3.2 落地差异（V1.1 核对）

| 实体 | 落地情况 |
|------|---------|

## 四、非功能需求

### 4.1 数据安全

> 本节表述已于 2026-10-26 逐句代码核实，除导出格式外与实现一致。

- 患者健康数据加密：**客户端**本地库 SQLCipher（AES-256）+ 云端备份 AES-GCM 端到端密文（服务端仅存密文、不可解密）✅ **属实**（仅移动 App；PC Web 数据存明文 localStorage，敏感操作建议走 App）；服务端解析/同步中转数据当前为**明文存储** ✅ 属实（解析任务与业务 CRUD 明文；密文快照通道除外）；字段级加密（AES-256-GCM DEK）为目标设计，尚未落地 ✅ 属实（客户端存在加密函数但无调用方；医生授权的 wrappedDek 再包裹除外）
- 本地存储优先，云同步可选 ✅（云同步为手动触发的端到端密文快照，详见 §4.2.7）
- **"用完即删"** ➕：解析确认后默认删除云端 PDF 原件（幂等，独立删除端点 + `sourceDeleted` 状态）；注意"用完即删"限原件，解析后的结构化数据按业务需要保留
- 数据导出支持 — ⚠️ **实际为 JSON / CSV / Excel(xlsx) + 浏览器打印**（App：CSV 多表 + JSON 备份；Web：JSON/CSV/Excel + 打印视图）；**PDF 文件生成与 DOCX 未实现**（V1.0 所写"JSON/PDF/DOCX"不实，已修正；打印视图可由用户另存为 PDF）
- 隐私设计对齐《个人信息保护法》医疗数据原则（本地优先、最小上传、明确授权）；正式合规需补 DPIA/授权流程文档，当前仓库未提供
- ➕ 安全加固（PRD 未记载的已实现项）：CORS 白名单 + 生产禁用 Swagger；登录/上传/会话/授权码多层限流 + XFF 默认不信任；生产配置守卫；文件路径穿越/IDOR 防护；Skill 正则 ReDoS 防护；社区发布脱敏白名单；推送 payload 不含病历信息；DPoP-lite 设备持有证明（服务端核心已实现，请求级验签待启用）

|--------|------|
| 首次使用者 | 无需等待AI解析，直接使用社区Skill，秒级出结果 |
| Skill贡献者 | 贡献积分/荣誉，优先使用社区高质量Skill |
| 社区整体 | 覆盖医院越多，新用户上手越快，形成网络效应 |

**医院格式覆盖率目标**（产品目标，当前无覆盖率统计）：
- V1.0：Top 50 三甲医院（覆盖80%+IBD患者）
- V2.0：Top 200 三甲医院
- 长期：全国所有三甲医院 + 主要二甲医院

### 5.4 患者社区 — ⚠️ 部分实现

## 六、竞品分析

| 产品 | 优势 | 不足 |
|------|------|------|
| 丁香医生 | 用户基数大，内容丰富 | 无IBD专属病程管理功能 |
| 微医 | 在线问诊便捷 | 数据管理碎片化 |
| MyCrohnsAndColitisTeam | IBD社区活跃 | 英文，无中国医院数据对接 |
| 各医院APP | 可查本院报告 | 数据孤岛，无跨院整合 |

**本产品差异化优势**：
1. **IBD专属**：针对克罗恩病和溃疡性结肠炎的全病程管理设计
2. **报告解析**：AI+Skill双引擎自动解析医院PDF检验报告，越用越准
3. **注射管理**：生物制剂专属的注射排期和提醒系统
4. **全病程视角**：检验+影像+内镜+用药+手术+症状的统一时间线
5. **就诊辅助**：一键生成结构化就诊摘要
6. **症状日记**：每日症状+排便+睡眠+压力的完整追踪，关联检验指标
7. **发作预警**：基于症状模式和检验数据的预警系统（当前为规则版，AI 版为目标）

## 八、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 医院PDF格式不统一 | 解析成功率低 | 优先适配Top10三甲医院格式，开放自定义模板 |
| 患者手动录入意愿低 | 数据不完整 | 以PDF自动解析为主，降低录入门槛 |
| 医疗数据合规风险 | 法律风险 | 数据本地存储优先，云同步需明确授权；补 DPIA/授权流程文档 |
| 专业医学术语门槛 | 用户理解困难 | 提供通俗化解释（如"钙卫蛋白=肠道炎症温度计"） |
| 竞品跟进 | 市场竞争 | 深耕IBD垂直领域，建立数据壁垒 |
| AI 解析准确性波动 | 数据质量 | 用户确认环节 + Skill 修正反馈 + 来源标记溯源 |
