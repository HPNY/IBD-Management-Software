## 1. 三条基本原则

**原则一：机器能判的，不占用人。**
格式、类型、未使用变量、依赖漏洞、构建失败，一律交给门禁（§7）。人工审查只回答机器答不了的问题：**这段逻辑在真实世界里对不对、会不会丢数据、会不会越权、用户会不会被误导。**

**原则二：审语义，不审风格。**
不评论个人偏好（命名口味、空行、括号位置）。风格由 `lint --fix` 决定；审阅意见只针对行为、边界、契约、风险。

**原则三：医疗数据默认高危。**
本项目处理检验值、用药、注射、内镜与手术史、症状日记。任何触及这些数据的变更，**默认按 C3 敏感变更审查**，除非作者能证明它只是展示层改动。

> 为什么强调这三条：本仓库 197/199 次提交来自 AI 代理，代码产出速度远高于人工阅读速度。若审查退化为"逐行看风格"，一定会在数量压力下失守。必须把审查预算集中在**数据正确性、授权边界、隐私泄露**这三类不可逆损失上。

## 2. 严重度定义

审查意见一律标注严重度。**严重度决定能否合并，不决定语气。**

| 级别 | 名称 | 判定标准 | 合并影响 |
|---|---|---|---|
| **S0** | 阻断 | 会造成患者数据丢失/损坏、隐私泄露、越权访问、核心流程不可用、生产启动失败、密钥泄露 | **禁止合并**，无豁免 |
| **S1** | 严重 | 特定条件下产生错误医疗数据或错误展示、静默失败（UI 显示成功但实际未生效）、非幂等导致重复写入、迁移不可回滚、缺少关键回归测试 | **禁止合并**；仅 hotfix 通道可在合并者+领域审查者双签下例外，且必须 24h 内补修并登记 |
| **S2** | 一般 | 边界条件未处理、校验缺失、错误提示不准确、缺少非关键测试、性能明显退化、文档与实现不一致 | 可合并，但**必须开 issue** 并指定期限（默认 2 周） |
| **S3** | 建议 | 可读性、可维护性、更优写法、补充注释 | 不阻塞，作者可拒绝并说明理由 |

**定级锚点**（避免争论，直接对号）：

- 涉及 `patientId` / `userId` 过滤缺失 → 至少 S0（越权）。
- `catch` 之后仍标记成功、或失败路径删除源数据 → S0（静默数据丢失）。
- 写多张表/多步状态变更但无事务 → S1。
- 接口字段命名/类型在前后端不一致 → S1（历史 C3 事故即此类）。
- 新增或修改备份/恢复/导出逻辑 → S1 起评（历史 H1/H2 事故）。
- 只在某平台生效的清单（AndroidManifest / Info.plist / 权限）变更 → S1（历史 H3 事故）。
- 纯文案、纯样式、纯注释 → S3。

## 3. 变更分级与审查深度

提交 PR 前，作者必须自行定级（PR 模板第一栏）。定级错误视为审查缺陷。

| 级别 | 典型变更 | 审查要求 | 必备证据 |
|---|---|---|---|
| **C1 轻量** | 文档、注释、文案、`.env.example`、脚本参数、纯样式 | 1 名审查者，可异步快速过 | 构建/类型检查通过 |
| **C2 常规** | 单模块功能增改、UI 交互、查询优化、非敏感接口调整 | 1 名审查者 + 机器门禁全绿 | 测试命令与输出、影响文件清单 |
| **C3 敏感** | 数据模型/迁移、API 契约、鉴权与 scope、加密与密钥、备份/恢复/导出、解析 Skill 与规则、文件上传、推送文案、隐私相关 | 1 名审查者 **+ 逐项走 §5 专项清单**，缺项不得合并 | 上述 + 专项清单逐条结论 + 负向用例 |
| **C4 破坏性/合规** | 破坏性 API 或数据迁移、权限模型变更、合规文案与知情同意、跨端协议变更 | 2 名审查者（含领域审查者）+ 回滚演练记录 | 上述 + 迁移 up/down 验证 + 回滚步骤实测 |

**C3/C4 不可由作者自行降级。** 定级争议由合并者裁决，裁决结论写入 PR 评论。

## 4. 审查范围边界（审什么、不审什么）

**必须审**：本次 diff 触及的行为、其调用方、其依赖的契约、其失败路径。
**必须顺带看一眼**：diff 直接调用的上游函数是否满足假设（例如新增 `find({ patientId })` 时，确认 `patientId` 来自归属校验而非入参）。
**不审**：与本次变更无关的历史代码。发现历史问题 → 记录为独立 issue，不在本 PR 扩大范围（约束 §1.9 禁止顺手重构）。

## 5. 审查维度与检查清单

按变更内容选择维度，**不必每次全跑**，但 C3 必须跑 §5.1–§5.5 与 §5.8。

### 5.1 正确性与契约

- [ ] 跨端字段命名是否一致？worker 输出 `snake_case`、API DTO、App/Web 读取的 `camelCase` —— 归一化是否收敛到**单一入口**，而不是各端各写一套映射？
- [ ] 类型是否在运行时有效？接口 DTO 是 `interface`（编译期擦除）还是带校验的 class？
- [ ] 数值/日期解析的失败分支是什么？定性值（"阴性"、"—"、"`"`）会不会变成 `NaN` / 抛错 / 静默置 0？
- [ ] 单位与量纲是否一致？（如 `白蛋白 g/L` 与 `前白蛋白 mg/L` 混入同一序列）
- [ ] 时区：涉及"今天/近 7 日/年度"的判定，用的是 UTC 还是本地日历日？
- [ ] 空值语义：`null` / `""` / `undefined` / 未传，四者行为是否都定义过？

### 5.2 数据完整性与持久化

- [ ] 多表/多步写入是否在同一事务内？失败是否整体回滚？
- [ ] 是否幂等？重复提交/重试/双击会产生重复行、重复顺延、重复扣减吗？
- [ ] ORM 条件是否用对了？**`where({ x: null })` 在 TypeORM 中会被丢弃或生成 `= NULL`（恒不匹配）**，必须用 `IsNull()`；`count/update/delete` 三类操作尤其危险。
- [ ] 迁移是否有 down 或补偿脚本？修复脚本是否幂等？
- [ ] 备份/恢复/导出：新增表是否同时进入"导出清单 + 导入清单 + 恢复计数"？三处是否引用**同一份 manifest**？
- [ ] 是否存在"删了再写"的窗口期？中途失败会不会留下空数据？
- [ ] 加密落盘路径是否残留明文副本（`.bak`、临时文件、导出 JSON）？清理路径是否存在且被执行？

### 5.3 授权与多租户

- [ ] 每个按 `patientId` 查询/写入的入口，是否都经过 `resolveOwnedPatientId`（或等价的归属校验）？**逐个入口看，不要因为"别的模块都做了"就跳过。**
- [ ] 是否接受客户端传入的 `id` / `patientId` / `objectKey` 并直接使用（mass-assignment / 覆盖主键 / 指定他人资源）？
- [ ] `@Public()` 或匿名会话（`parse_session` / `community` / `sync_session`）能否触达写路径？匿名会话的权限是否被当成"已认证"？
- [ ] scope 守卫是否 fail-open？缺 user 时默认给什么？
- [ ] 删除/覆盖类操作是否有二次确认或短期凭证？

### 5.4 隐私与合规

- [ ] 日志、错误信息、监控上报是否含 PHI（药名、检验值、诊断、医院名）？**异常对象整体 `console.log(err)` 也算。**
- [ ] 推送/通知 payload 是否零病历字段？是否复用了已有的禁词表测试？
- [ ] 测试数据是否合成/脱敏？fixture 是否与生产字段一致（否则测试假绿）？
- [ ] 新增用户可见页面是否带"非诊断、非治疗建议"声明？
- [ ] 是否扩大了采集范围或授权范围？（扩大即 C4，需暂停确认）
- [ ] 密钥/凭据/真实患者数据是否进入仓库、示例文件、CI 日志？

### 5.5 客户端状态与生命周期

- [ ] 页面首次进入是否加载了已存在的数据？（`initState` 是否调用了 `_load...`；`IndexedStack` 长驻的 Tab 是否会陈旧？）
- [ ] `await` 之后 `setState` 前是否检查 `mounted`？controller / listener / timer 是否 `dispose`？
- [ ] 跨日、跨 Tab、前后台切换后，状态是否重绑？昨天的值会不会写进今天？
- [ ] 保存类按钮是否有 in-flight 保护（防重复提交）？
- [ ] 平台清单是否闭环：Android 的权限/Receiver、iOS 的 `Info.plist`、插件 README 要求的声明是否齐备？**"代码写对了"不等于"会生效"。**
- [ ] 失败时 UI 是否如实显示失败？有没有"提示成功但实际没写进去"？

### 5.6 错误处理与可观测性

- [ ] `catch` 块做了什么？是否吞掉异常后继续执行后续"成功"逻辑？
- [ ] 失败路径是否产生副作用（删文件、删记录、改状态）？
- [ ] 是否有静默 `no-op`（条件永不匹配导致 `affected = 0` 但无告警）？写操作后是否检查 `affected`？
- [ ] 错误是否可定位（含任务/实体标识，但不含 PHI）？
- [ ] 外部依赖（LLM、FCM、S3、Redis）超时/非预期响应是否有兜底，而不是冒泡成 500？

### 5.7 测试质量

- [ ] 新增/修改逻辑是否有对应测试？修改行为是否更新了回归测试？
- [ ] 断言是否真实？有没有恒真断言、只断言"不抛异常"、只断言 HTTP 200？
- [ ] 负向用例是否存在（越权、非法输入、重复提交、空配置）？
- [ ] 测试是否真的覆盖生产路径？（复制一份 SQL 来测、用生产不会出现的 fixture，都算未覆盖）
- [ ] 该跑的门禁是否在 CI 里跑？（本地跑过 ≠ CI 会跑；PR 阶段不跑的检查等于没有）
- [ ] 无法运行测试时，是否明确标 `BLOCKED` 并说明原因，而不是默认通过？

### 5.8 配置、依赖与部署

- [ ] 新增环境变量是否同时更新：`.env.example`、compose、`env-guard`、配置文档？四处缺一即 S1（部署会挂或静默失效）。
- [ ] 空字符串 vs 未设置：`${VAR:-}` 会把变量设为空串，`??` 不会回落默认值。空值语义是否显式处理？
- [ ] 默认值是否安全？开发便利开关（如免验证码登录）在生产是否强制关闭？
- [ ] 生产占位符（`change-me-*`、`dev-*`）是否被 env-guard 拒绝？
- [ ] 依赖升级是否有理由、锁文件是否更新、是否跑过审计？
- [ ] 工具链版本是否锁定（Node/Flutter/Python/镜像 tag）？未锁定视为 S2，影响可复现构建时升 S1。

## 6. 项目专属红线清单（复发型反模式）

以下每一条都在本仓库真实发生过（见 2026-10-29 报告）。**看到左侧模式，必须去查右侧后果**，无需再讨论是否需要修。

| # | 看到这个模式 | 必须检查 | 典型后果 |
|---|---|---|---|
| R1 | `where({ field: null })` / `count/update/delete` 带 null 条件 | 改 `IsNull()`；写后校验 `affected` | 条件被丢弃或恒不匹配 → 更新 0 行、删除 0 行、重复插入 |
| R2 | 跨端读写同一份数据，两侧各写一套字段映射 | 收敛到单一归一化入口 + 契约测试 | 一侧读不到字段 → 主功能全废且 UI 显示成功 |
| R3 | `catch { ... }` 后继续 `patch(status: done)` / `delete(...)` | 失败不得标成功、不得删源数据 | 数据丢失且用户以为成功 |
| R4 | `find({ where: { patientId } })` 且 `patientId` 来自入参 | 改 `resolveOwnedPatientId` | 跨租户读取他人 PHI |
| R5 | 多步写库无 `transaction` | 包事务 + 前置校验 | 中途失败留下半成品（停药无替代、重复计划） |
| R6 | `process.env.X ?? "default"` 且 compose 用 `${X:-}` | 空串按未设置处理；显式拒绝空值 | 安全开关静默失效（免验证码登录） |
| R7 | UI 先提示成功、后发请求 / 不校验响应 | 以服务端结果为准 | 用户以为已保存，实际未落库 |
| R8 | `LIKE '%指标名%'` 做指标匹配 | 精确匹配或别名白名单 | 相似指标串味（量级差千倍） |
| R9 | 长驻 Tab / 页面只在 `initState` 初始化一次 | 首屏加载 + 可见时刷新 | 冷启动显示"暂无数据"，既有记录不可达 |
| R10 | 依赖平台清单的能力（通知、后台、权限、深链） | 对照插件 README 逐项核对 manifest/plist | 代码正确但功能从不触发，且无报错 |
| R11 | 明文/临时副本写入用户目录或 `Documents` | 明确清理路径 + 回归断言"文件不存在" | 加密设计失效，PHI 长期明文留存 |
| R12 | 测试 fixture 与生产字段不一致 / 断言恒真 | 用生产同构数据；断言具体值 | CI 全绿但线上必挂 |
| R13 | 时间用 UTC 日历日 / 用"最近 N 条"代替"最近 N 天" | 明确时区与区间语义 | 东八区判错日、告警失真 |

**红线命中即定级**：R1/R2/R3/R4 命中 → 至少 S1；造成数据丢失或越权 → S0。不适用"历史遗留所以先放过"。

## 7. 合并门禁

四级门禁，前一级不过不进下一级。

### G0 · 机器门禁（必须全绿，不可人工豁免）

| 检查 | 现状（T8 落地后） | 要求 / 遗留 |
|---|---|---|
| 全 workspace `typecheck` | ✅ `ci.yml` 已新增 `Typecheck (all packages)` job | `api-client` / `ui-tokens` 无 tsconfig，会被 `-r --if-present` 静默跳过（T8.6） |
| 构建 | ✅ `build:api` / web / doctor-web | 保持 |
| Flutter `analyze` + `test` | ✅ CI 已跑 | 保持；warning/error 阻塞 |
| Python 单测 | ✅ 2 个用例 | 保持，随改动扩充 |
| 依赖审计 `pnpm audit --prod --audit-level=high` | ✅ CI 已跑 | 保持为 0 |
| **TS lint** | ✅ `eslint.config.mjs` + `pnpm lint`（0 error / 9 warning，151 文件） | 存量 17 项已基线化于 `eslint-suppressions.json`，修复任务 T8.5 |
| **格式检查** | ✅ `pnpm format:check`（仅本次变更文件，见 `scripts/check-format-changed.mjs`） | 存量未重排，随改动自然收敛；Dart 侧待接（T8.7） |
| **PR 阶段 fullstack E2E** | ✅ `ci-fullstack.yml` 已加 `pull_request` 触发 | 有 paths 过滤，配置分支保护时注意 pending 问题（见 [branch-protection.md](branch-protection.md) §3） |
| **敏感信息扫描** | ✅ `scripts/scan-secrets.mjs`（全仓 65,658 行 0 误报） | 兑现 `docs/security-checklist.md` 1.5「推送前扫描」 |
| **硬规则 1（无任务号不开 PR）** | ✅ `pr-guard.yml` + `scripts/pr-guard.mjs` | 校验任务号、描述章节、定级、勾选数、证据区 |
| **硬规则 2（G0 未绿不合并）** | ⬜ **需仓库管理员手动开启分支保护** | 配置步骤见 [branch-protection.md](branch-protection.md)；未开启前该规则仅为流程约束 |

#### G0 基线的维护方式（ESLint suppressions）

存量 17 项违规记录在 `eslint-suppressions.json`，按「文件 + 规则 + 条数」计数。行为已实测：

| 场景 | 结果 | 处理 |
|---|---|---|
| 新增违规 | 超过基线计数 → **error，exit 1** | 必须修，不能加基线（新增问题不接受基线化） |
| 修掉存量违规 | 基线计数多于实际 → **exit 2**，提示 `--prune-suppressions` | 执行 `pnpm lint:prune` 收缩基线并随 PR 提交 |

> 这意味着 **T8.5 每修掉一项，必须同时提交收缩后的基线**。基线文件是"债务台账"，只减不增。

### G1 · 作者自查（PR 模板逐项勾选，缺项即退回）

自查不是形式。**每一条勾选都要能在 PR 里找到对应证据**（命令输出、文件路径、测试名）。无证据的勾选视为未完成。

### G2 · 同行审查（按 §3 分级执行）

审查者必须在 PR 上留下**结论性意见**：`Approve` / `Request changes` / `Comment`。沉默不算通过。

### G3 · 专项审查（C3/C4 强制）

安全、隐私、数据一致性三类专项清单，逐条给结论（通过 / 不适用 / 不通过）。不通过项不得以"后续补"合并。

## 8. 豁免与例外

豁免只有两种合法情形：

1. **Hotfix 通道**：线上 S0 故障。允许 S1 在双签下先行合并，但必须在 PR 中写明：故障现象、临时方案、补修任务号、补修期限（≤24h）。
2. **无法验证项**：依赖真实凭据/真机/法务确认。标 `BLOCKED`，写明"未验证"与"验证方式"，**不得声称通过**（约束 §1.5）。

豁免记录统一写入 PR 评论，并在月度复盘时统计。**S0 无豁免通道。**

## 9. 度量（看复发，不看数量）

审查机制是否有效，不看"提了多少意见"，看这五个数：

| 指标 | 定义 | 目标 |
|---|---|---|
| **逃逸缺陷数** | 合并后才发现的问题，按 S0/S1 分别计数 | S0 逃逸 = 0；S1 逃逸逐季下降 |
| **红线复发次数** | §6 中 R1–R13 在合并后再次出现的次数 | 同一红线复发 ≤1 次/季度（复发说明标准未被执行，而非标准缺失） |
| **门禁覆盖率** | 走完 G0–G3 的 PR 占比 | ≥95% |
| **PR 中位规模** | 有效 diff 行数（排除生成物/lock/迁移） | ≤400 行 |
| **返工轮次** | 单个 PR 的 `Request changes` 次数 | ≤2 轮；第 3 轮强制结对 |

度量数据按月汇总，写入 `docs/code-review-YYYY-MM.md`，与审查报告同目录。

## 10. 审查意见书写规范

一条合格的审查意见包含四要素，缺一即视为无效意见（作者可不响应）：

```
[S1] services/api/src/modules/x/x.service.ts:186
问题：副作用查询未按 patientId 过滤，任意 token 可读取全库 adverseEvents。
证据：innerJoin 仅用于取药名，无 patient/user 条件；冒烟测试只校验 chainText，无法发现。
建议：innerJoin(..., "m.id = ae.medicationId AND m.patientId = :pid")；补一条"两个患者各有副作用"的用例，断言只返回本人。
```

- **指位置**：文件 + 行号，或函数名。
- **说影响**：对用户/数据的实际后果，不是"不符合规范"。
- **给证据**：代码路径、复现方式、测试缺失点。
- **给方向**：至少一个可执行替代方案。禁止只说"这里有问题"。

**用语分级**（与严重度解耦，避免把 S3 写成命令）：

- `must` —— 对应 S0/S1，不修不能合并。
- `should` —— 对应 S2，建议本次修，或开 issue。
- `nit` —— 对应 S3，作者可忽略。
- `question` —— 审查者不确定，需作者解释；作者解释成立即关闭。
- `praise` —— 值得保留的写法。**每条审查至少留一条**，否则审查会退化为挑错。

## 附录 A · 一页速查（打印用）

**提 PR 前**：定级 → 自查 12 项 → 贴命令与输出 → diff ≤400 行。
**看 PR 时**：读描述与证据 → 看 diff 结构 → 按 §5 选维度 → 查 §6 红线 → 给四要素意见 → 结论。
**判定**：S0 一律拒；S1 默认拒（hotfix 双签例外）；S2 开 issue；S3 随作者。
**永远记住**：这个仓库的错误代价是**患者的医疗记录**。宁可多问一句"这个字段哪来的"，不要放过一个没有归属校验的查询。
