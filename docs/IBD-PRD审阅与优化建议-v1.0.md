# IBD PRD 审阅与优化建议 v1.0

> **审阅对象**：`docs/IBD病程管理程序PRD-v1.2.md`（2026-10-27，1064 行）× 代码实测（2026-10-29）
> **配套文档**：[IBD 模块功能规格 v1.0](IBD模块功能规格-v1.0.md)（26 个模块的逐功能定义）
> **一句话结论**：PRD v1.2 已经是一份**诚实对齐实现**的文档，但作为**需求文档**仍不合格——它承诺了大量不可验收的"自动/智能"，回避了"无登录墙却需要账号"的架构矛盾，并用里程碑的"✅"掩盖了一批**半成品与死代码**。本文给出全部歧义（A）、优化（O）、冗余判断（X）与简化方案（S）。

## 一、审阅结论（先看这一页）

### 1.1 总体判断

| 维度 | 判断 | 依据 |
|------|------|------|
| **完整性** | 功能覆盖很全（26 个模块、193 个功能点） | 见功能规格 |

| **功能必要性** | ⚠️ 41 项需处置（12 删、10 合并、9 降级、10 简化） | X 系列 77 条（唯一 ID） |

### 1.2 最该先解决的 6 件事（按严重度排序）

| # | 问题 | 用户会怎么感受 | 处置 | 优先级 |
|---|------|--------------|------|--------|
| 1 | **患者侧云端功能在"无登录墙"设计下不可达**（空 Bearer → 恒 401） | "我的医生/同城病友/药物评价/小程序检验"永远是空的或报错 | 统一匿名会话策略，或先隐藏入口 | **P0** |
| 2 | **数据资产不闭环**：备份导出 8 类数据、恢复只回填 3 类；检查/手术/不良反应/服药打卡从未导出 | 换手机后手术史、检查记录消失；重复恢复数据翻倍 | 补全备份/恢复 + 去重 + 导出补缺 | **P0** |
| 3 | **每日打卡"1 分钟"是靠默认值堆出来的** | 越省事记录越假：不填 = 腹痛 0 分 / Bristol 4 型 / 无血，还会自动生成一条"正常"排便 | 空值语义改 null + 首屏 4 项 + 吸底保存 | **P0** |
| 4 | **检验记录不能改、不能删、没有列表** | 解析错一个数，错一整年；趋势被污染 | 加记录列表 + 编辑/删除 + 去重 | **P0** |
| 5 | **"分析"被切成三处且互相打架**（仪表盘 / 规则分析 / 发作预警） | 同一份日记，一个页面说"正常"，另一个说"警告" | 总览 / 唯一预警出口 / 解释明细 三分工 | **P1** |
| 6 | **半成品与死代码在消耗信任**：死链、伪按钮、空壳开关、演示数据 | 点"检验套餐模板"→ 404；开"简洁模式"没变化 | 每项"补/删/藏"三选一 | **P1** |

### 1.3 审阅过程中被证实、且必须写进 PRD 的三条事实

1. **App 端解析不回写服务端业务数据**：上传→轮询→删原件→存本机，全程不调用 `confirm`（`lab_entry_page.dart:356-393`）；服务端只留下解析任务（ParseJob），没有检验结果、也不生成解析模板。因此"用户确认后自动生成 Skill"在 App 不成立，服务端模板只由 PC Web 批量解析创建（`parse.service.ts:200-214`、`ParseBatch.tsx:94`）。
2. **生产环境拿不到患者 `full` token**：手机验证码登录在生产被硬关闭（`auth.service.ts:76-78`），而匿名会话只有 `parse_session / sync_ciphertext / push_register / community` 四种 scope（`auth.service.ts:178-201`）；`/labs` 等业务接口要求 `scope=full`（`lab.controller.ts:9-11`）。
3. **三处患者侧页面用空字符串 token 调接口**：`my_doctors_page.dart:81`、`geo_community_page.dart:47`、`drug_review_page.dart:62` 都用 `AuthSession.parseSession('', uuid)`，`authHeaders` 会发出 `Bearer `（空令牌）（`auth_session.dart:109-115`），全局 `JwtAuthGuard` 直接 401（`jwt-auth.guard.ts:29-50`、`auth.module.ts:36-37`）。

> 这三条不是"实现细节"，而是**产品定位与架构的冲突**：PRD §4.2.7 说"无登录墙、核心功能不依赖账号"，但 V2 的医生协作、社区、小程序查看全部挂在需要登录的接口上。PRD 必须二选一：**要么为这些能力提供匿名短会话（推荐）**，**要么承认它们需要账号并在 PRD 标注 ❌**。

## 二、审阅方法与判定标准

### 2.1 三源对照

| 来源 | 用途 | 处理原则 |
|------|------|---------|
| PRD v1.2 | 需求意图与承诺 | 只作为"被审阅对象"，不采信其"实现状态"标注 |
| 代码（4 端 + 2 服务） | 功能是否存在、字段是否落库 | **最高权威**；每条判断给 `path:line` |
| 历史证据（`docs/audit-evidence/`、`docs/compose/spec/`） | 已知结论 | 抽查后引用；与代码冲突时以代码为准 |

### 2.2 四条判定档位

- **A 歧义**：会让开发/测试/用户产生不同理解（术语、边界、状态、跨端、无可验收标准）。
- **O 优化**：不改变功能，但能显著降低操作成本或理解成本。
- **X 无意义/冗余**：只有四种处置——**删除 / 合并 / 降级（隐藏或延后）/ 保留但简化**；写"保留"必须给理由。
- **S 简化**：可量化的操作成本改善（步数、字段数、屏数、通知条数）。

### 2.3 可信度与未验证项（如实声明）

| 项 | 状态 |
|----|------|

## 三、六个系统性问题（跨模块，必须先决策）

### SYS-1 患者侧云端链路不可达：无登录墙 ≠ 不需要身份

**现象**：医生授权、同城病友、药物评价、小程序检验查看，四类"社区/协作"能力在 App/小程序端全部拿不到数据（空态或错误），因为它们调用的是需要登录的接口，而客户端只发送空令牌。

**证据链**（全部代码可查）：

```text
my_doctors_page.dart:81 / geo_community_page.dart:47 / drug_review_page.dart:62
  └─ AuthSession.parseSession('', uuid)          # accessToken = ''
       └─ authHeaders() → 'Bearer ' (空令牌)      # auth_session.dart:109-115
            └─ JwtAuthGuard（全局 APP_GUARD）      # auth.module.ts:36-37
                 └─ header 有 Bearer 但 token 空 → 401 invalid or expired   # jwt-auth.guard.ts:29-50

生产环境无法获得 full token：
  auth.service.ts:76-78   IS_PROD → 'sms login disabled in production'
  auth.service.ts:178-201 匿名会话 scope 仅 parse_session / sync_ciphertext / push_register / community
  lab.controller.ts:9-11  @UseGuards(RequireScope("full")) ← 小程序 listLabs() 无 token（miniapp/src/lib/api.ts:31-56）
  SkillCommunity.tsx:46   读 'ibd_app_user_uuid'，但 Web 全仓只写 'ibd_web_uid'（ParseBatch.tsx:43-46）→ 匿名会话 400
```

**用户影响**：这四处在 PRD §4.2.6 矩阵里标为"✅ 社区互动 / ✅ 检验查看 / ✅ Skill 社区"，验收时会被判"通过"，上线后用户看到的是永远的空列表或报错——比没有更伤信任。

**建议（必须二选一，不能继续模糊）**：

- **方案 A（推荐）**：把"匿名身份"补齐为真实能力。客户端为每类能力申请对应 scope 的短会话（社区已有 `community`、医生授权建议新增 `care_link` scope），服务端按 scope 白名单放行；App 端 3 处改为真实会话，小程序 `listLabs` 改为只读摘要或申请 `community`/只读 scope。
- **方案 B（快速止血）**：暂时隐藏这 4 个入口（App 3 张卡 + 小程序检验页），PRD 矩阵改为 ❌，并写明"需要账号的 V2 能力"。

**验收**：任一入口在未登录状态下要么给出真实数据，要么给出"需登录/需授权"的明确引导，**不允许出现空列表冒充"暂无数据"**。

### SYS-2 数据资产不闭环：备份/恢复/导出三本账

**现象**：患者最怕的不是记录麻烦，是"记录没了"。当前备份与恢复严重不对称。

| 数据 | 导出备份 | 恢复 | CSV/Excel 导出 | 云端快照 |
|------|:---:|:---:|:---:|:---:|
| 检验 labs | ✅ | ✅ | ✅ | ✅（密文） |
| 用药 medications | ✅ | ✅ | ✅ | ✅ |
| 注射 injections | ✅ | ✅ | ✅ | ✅ |
| 症状日记 symptoms | ✅ | ❌ | ✅ | ⚠️ 服务端仅 8 列，缺睡眠/口腔/关节/自定义 |
| 排便 bathroom | ✅ | ❌ | ⚠️ | ⚠️ 无服务端实体 |
| 量表 surveys | ✅ | ❌ | ✅ | ⚠️ |
| 饮食 foodLogs | ✅ | ❌ | ❌（A1/B 核实无 food CSV） | ⚠️ |
| 药物评价 drugReviews | ✅ | ❌ | ❌ | ⚠️ |
| **检查 exams** | ❌ **从未导出** | ❌ | ❌ | ❌ 无服务端实体 |
| **手术 surgeries** | ❌ **从未导出** | ❌ | ❌ | ❌ |
| **不良反应 adverse_events** | ❌ | ❌ | ❌ | ❌ |
| **服药打卡 med checkins** | ❌ | ❌ | ❌ | ❌ |

证据：`backup_service.dart:55-71`（导出 8 类数据 + 技能计数 + 3 个元字段，共 12 键）vs `:86-138`（只回填 labs/medications/injections）；`data_exporter.dart:172-178`（5 个 CSV 不含检查/手术/饮食/不良反应）。

**附加缺陷**：恢复是**追加式**（`insert` 而非 upsert），同一备份恢复两次 → 数据翻倍；恢复前无"将追加、不清空"的提示。

**建议**：
1. 备份/恢复改为**同一份 schema**：导出什么就必须能恢复什么；恢复用 `date+医院` 或原 id 幂等去重。
2. 导出补 `exams`/`surgeries`/`adverseEvents`/`medCheckins`；至少保证"低频高价值"的手术史不丢。
3. 恢复前显示快照时间、条数、将追加的明细；恢复后给"新增 X / 跳过 Y"报告。
4. 优先级：**P0**（这是数据资产级缺陷，比任何新功能都重要）。

### SYS-3 入口税：功能越多，所有功能越难找

**现象**：App"分析"Tab 是 14 张平铺卡片（`analysis_tab.dart:29-168`）：指标趋势、病程时间线、检查与手术、排便细表、食物与排便、就诊摘要、发作预警、AI/规则分析、药物评价、同城病友、我的医生、生活质量量表、年度报告、数据导出。**没有分组、没有分组标题、没有频率排序**。找"数据导出"要滚 2 屏；找"年度报告"是第 13 张。

**跨模块重复叙事**（同一件事有 2–3 个"家"）：

| 事情 | 出现在 | 问题 |
|------|--------|------|
| 用药调整记录 | 用药历史（按条）、病程时间线（开始/停药事件）、年度报告（"变更"= 用过的药条数） | 三套口径，年报"变更"文案错 |
| 给医生看的文本 | App 就诊摘要、医生端 `summaryText`、年度报告 | 字段与尾注不一致，患者与医生看到的不是同一份 |
| 排便数据 | 打卡表单（4–6 字段）、独立"排便细表"页（6 字段） | 两处录入、两套便血档位，且打卡会自动生成一条排便记录 |
| 分析结论 | 首页活动度卡、规则分析页、发作预警页 | 两套阈值同时存在，结论可能互相矛盾 |

**建议**：分析 Tab 从 14 → 4 组（看变化 / 看记录 / 看结论 / 分享与连接），每组默认展开前 3 项；三项重复叙事各收敛为"唯一权威"（详见第七节）。

### SYS-4 每日录入：1 分钟靠默认值，数据可信度被牺牲

**可量化事实**（B 组逐控件统计）：

- 打卡表单 **20 个字段组 / 21 个数据列 / 44 个可点可拖控件**（7 滑块、8 开关、28 单选芯片、1 步进器）；
- **必填 0 项**，无任何校验；估算总高 ≈3,150 dp，720 dp 视口 **≈4.4 屏**，保存按钮在屏幕最底部；
- 速记路径 = 2 次点击（"和昨天一样"+"保存"）+ 4–5 次上滑 ≈15 秒；完整记录 ≈40–60 秒。

**代价**：
1. **两套空值语义**：症状字段恒写 `0 / 4 / none`（`symptom_page.dart:238-253`、`repositories.dart:280-310`），睡眠压力 6 列写 `null`——"没记录"与"记录为 0"在数据库里分不开。
2. **打卡凭空生成排便记录**：`hasBathroomPayload` 恒为真（`repositories.dart:257-262`），只填腹痛的用户也会写出一条"Bristol 4 · 0 次 · 无血"。
3. **预警读伪数据、且红黄失衡**：只有 1–2 条日记时落进绿色"正常"分支（`flare_service.dart:74-107`），并因默认值把"没填"当"没症状"；同时"擦拭有血"（trace）直接判为最高级 🔴（`flare_service.dart:40-48`），门槛过低。
4. **量表同病**：PHQ-9 未答项按 0 计 = "无或极轻微"；第 9 题（自伤念头）仅有静态提示，评分后无强制求助卡（`survey_kit.dart:37-49`、`survey_page.dart:33-36`）。

**建议**：见第 7.2 节"打卡重构"——首屏 4 项、其余折叠、未触碰写 `null`、保存吸底、停止自动生成排便记录、补录入口、预警加样本门槛。

> 判定标准：**重复**（同一件事两个入口/两次填写）、**低价值**（目标用户几乎不用，或用了不改变决策）、**不可用**（有模型无入口/有按钮无行为）、**合规风险**、**成本>>收益**。处置只有四档：删除 / 合并 / 降级 / 保留但简化。

### 5.1 结论

77 个唯一 X 条目（同一 ID 会在模块 4.7 与组审阅表重复出现，按行计 139 次）归并为 **41 项需要处置**：

| 处置 | 数量 | 含义 |
|------|:---:|------|
| **删除** | 12 | 无实现、无入口、无消费方，或违反最小披露/合规 |
| **合并** | 10 | 同一件事有 2–3 个家，用户与开发都要维护多份 |
| **降级** | 9 | 有价值但当前条件不成立（无用户基数/无数据链路/无到期机制） |
| **保留但简化** | 10 | 方向对，但交互或范围需要收窄（见第七节） |

**明确判定为"保留（不无意义）"的功能**（避免误删）：检验解析与趋势、用药方案、注射排期、病程时间线、就诊摘要、年度报告、每日打卡、发作预警、提醒、活动度仪表盘、导出备份、Skill 模板。它们的共同点是**回答了一个患者真实会问的问题**，问题出在"怎么做"，不在"要不要做"。

## 七、简化方案：把 26 个模块收敛成 6 个"患者任务"

> 这一节是"简单易操作"的落地版：不是再加功能，而是**减少入口、减少字段、减少决策**。每条给出 before → after 与可验收口径。

### 7.1 入口：分析 Tab 14 张卡片 → 4 组

| | 现状 | 目标 |
|---|------|------|
| 结构 | 14 张无分组卡片平铺（`analysis_tab.dart:29-168`） | 4 组，每组标题 + 默认展开前 3 项 |
| 分组 | — | ① **看变化**：指标趋势 / 病程时间线 / 疾病活动度 ② **看记录**：检查与手术 / 排便细表 / 食物与排便 ③ **看结论**：就诊摘要 / 年度报告 / 近期提示（预警+规则分析合并） ④ **分享与连接**：药物评价 / 同城病友 / 我的医生 / 数据导出 / 生活质量量表 |
| 验收 | 找"数据导出"需滚 2 屏 | 任一功能 ≤1 次展开、≤3 次点击可达 |

**为什么不是"删功能"**：患者确实需要这些能力，问题只是它们被平铺成了一条长菜单。分组让新增功能不再稀释旧功能。

### 7.2 打卡：从"4.4 屏表单"到"1 屏 4 项 + 折叠"

| | 现状 | 目标 |
|---|------|------|
| 首屏 | 快捷模板 + 日历，核心 4 项要滚 1 屏才见 | 首屏固定 4 项：腹痛 / 排便次数 / Bristol / 整体感受 |
| 其余 | 20 字段组全部平铺 | "睡眠与压力""更多症状"两组折叠；睡眠质量加锚点 |
| 保存 | 按钮在表单最底部 | 吸底常驻 + 顶部"已改 N 项" |
| 空值 | 未触碰也写 0/4/none，并自动生成排便记录 | 未触碰写 `null`；不自动生成排便记录（用户点"加一次排便"才写） |
| 速记 | "和昨天一样"预填后还要滚到最底保存 | "和昨天一样"= 预填 + 立即保存 + 可撤销 |
| 补录 | 日历格只能看 | 点灰色格 → "补录这天" |
| 验收 | 完整记录 ≈40–60s；速记 2 击 + 4–5 上滑 | 速记 1–2 击；完整记录 ≤60s；未记录与 0 分可区分 |

### 7.3 分析：三处入口 → 三句分工

| 入口 | 只回答 | 不做什么 |
|------|--------|---------|
| 首页活动度卡 | "我现在整体怎么样？"（三灯 + 下次注射） | 不给结论、不做分级 |
| 近期提示（原发作预警） | "有没有需要马上处理的情况？"（唯一红黄绿出口） | 不在别处重复判定；样本 <3 天不给结论 |
| 规则分析（改名） | "为什么？"（趋势方向、均值对比、触发条件） | 不预测、不给建议、不重复预警规则 |

**验收**：同一份日记，三个入口不能给出互相矛盾的结论；规则页只能从预警下钻。

### 7.4 量表：4 个并列 → 2 个默认 + 2 个折叠

- 默认：PHQ-9（心理健康）+ MiniQoL（5 题）。
- 折叠：SF-36、IBDQ 收进"更多量表"，并标注"自管简化分，非标准常模"。
- 规则：未答完不保存；Q9≥1 弹求助卡；建议每 30 天做一次 + 入口角标（不做推送）。
- 验收：完成一次默认量表 ≤2 分钟；任何结果都能看到"上次分数"。

### 7.5 提醒：从"按对象轰炸"到"每日 ≤2 条"

- 注射：同一针多个提前量合并为 1 条（"距下次注射 3 天"），已过时刻不补弹。
- 用药：同日多药合并为 1 条（"今日有 N 项用药待确认"），点击进打卡。
- 复查：仅本机一次性闹钟（1 个日期 + 固定 9:00），不含项目。
- 预算：每日 ≤2 条；文案不含药名/剂量/病名（已有禁词测试）。
- 验收：设置 4 个提前量后，同一针只收到 1 条通知。

### 7.6 数据资产：三本账 → 一个"数据与备份"页

| 段 | 内容 | 验收 |
|----|------|------|
| 给医生 | 「复制就诊摘要」+「导出 CSV/XLSX」（检查/手术必含） | 3 步内拿到文件/文本 |
| 完整备份 | 「导出 JSON 备份」+「从备份恢复」（幂等去重、列清单） | 恢复两次不产生重复数据 |
| 云端（可选） | 「上传密文快照」+「从云端恢复」+ 上次快照时间/大小/版本 | 恢复前能看到"将要恢复什么" |

**必须补的合规提示**：导出/分享 = 数据离开加密存储（`export_page.dart:67` 目前只有一个空警示卡），补一行明文风险提示。

### 7.7 检验记录：只进不出 → 可管理

现状：`LabRepository` 只有 `insert/listAll`（`repositories.dart:9-62`），**没有记录列表、不能改、不能删**；重复上传同一报告会重复插入。

目标：① 检验记录列表（按日期倒序、显示 N 项/异常数/来源）；② 单条编辑/删除；③ 同"日期+医院"导入时提示合并/新建/覆盖；④ 趋势页可点数据点跳回该条记录。

**这是"敢不敢用"的底线**：解析错一个数，用户无法修正，就会放弃整个功能。
