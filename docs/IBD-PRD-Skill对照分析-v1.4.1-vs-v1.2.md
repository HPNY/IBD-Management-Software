## 0. 一句话结论

PRD v1.2 仍是一份"**对齐代码实现**"的文档：它把 App/服务端做到了什么写得很诚实，但它对齐的是**代码现状**，不是 **Skill 侧已在真实病历上验证过的临床口径**。因此 V1.2 里同时存在两类偏差：

1. **医学标准口径错误或过窄**（钙卫蛋白单一 `<200` 与"缓解线"、SES-CD 无总分口径、Limberg 当独立活动度指标、SF-36/IBDQ 命名与可比性、IBUS-SAS"未支持"一词过宽）；
2. **Skill 已跑通、PRD 未覆盖的能力**（检查 PDF 解析与 `activity_score`、待核对队列/已处理清单/去重键、接种筛查、就诊记录、营养体重、用药监测与变更史、轻量心理、规则化预警与待办、统一时间轴），且**部分代码事实与 PRD 表述相反**（最典型：注射"延迟自动顺延"——PRD 写"未实现"，服务端其实已实现且默认开启，而 Skill 的规则恰恰是"不自动顺延、以医嘱为准"）。

V1.3 的处置原则：**先区分"Skill 侧跑通 / App 已实现 / 目标设计"三层事实，再改口径；医学阈值必须标来源；只记录不诊断的边界写成全局章节。**

## 3. 代码事实与 PRD 表述相反的两处（V1.2 必须改）

### 3.1 注射"延迟顺延"：PRD 写"未实现"，代码其实默认开启

- PRD v1.2 L293：「延迟注射后自动调整后续排期 ❌ 未实现（记录实际日期后，后续计划日期不顺延）」。
- 代码事实：服务端 `InjectionService.complete()`（`services/api/src/modules/injection/injection.service.ts:137-190`）在 `rescheduleDelay !== false`（**默认 true**）且实际晚于计划时，把同药后续未完成计划的 `plannedDate` 全部 +delayDays。App 端本地完成（`repositories.dart:192-200`）只写实际日期、不顺延，且 App 的 `completeInjection` 客户端方法无调用方。
- Skill 规则：**以最新医嘱/预约日期为准，不自动顺延；+56 天只作校验；不自动改写医嘱**。
- 处置：V1.3 §2.2.3 把"顺延"从"待实现功能"改为**明确的设计边界**，并标注服务端现状与冲突；`Injection` 增 `nextAppointment/scheduleRule/rescheduleLog`；工作清单 V13-20/V13-35 要求 `rescheduleDelay` 默认关闭或二次确认。另按用户 **2026-11-02 补充**：医生对注射前后相差数天无强烈反对；实际日期与计划/预约相差 ≥1 天时**可**补充偏差原因（7 值枚举）+ 备注（非强制、不阻断，患者端记录不等同医院存档），系统计算偏差天数，不据此改医嘱（清单 V13-44）。

### 3.2 `IBUS-SAS 未支持`：App 确无，但"未支持"一词抹掉了 Skill 已验证的分层能力

- 代码事实：全仓无 `IBUS` 解析；仪表盘/详情页只对 `score`/`findings` 做正则，提取 Limberg 与 SES-CD（`activity_service.dart:52-72`，用于 `activity_detail_page.dart:94-110,267-275`）。
- 处置：V1.3 改为三档状态（Skill 侧可记录原文/数值 → App 仅自由文本 → 数值化/趋势未做），并把 Limberg 明确为"血流分级，需结合肠壁厚度/分层"。
