# 代码审查流程（Code Review Process）

- 文档状态：**已生效 · 项目级流程**
- 建立日期：2026-11-12
- 配套标准：[code-review-standard.md](code-review-standard.md)（严重度、分级、检查清单、门禁定义均在标准中，本文只讲"怎么做、谁做、何时做"）

---

## 1. 设计前提（为什么流程长这样）

本仓库的实际协作形态是：**1 名人类负责人 + 多个 AI 编码代理**（`git shortlog` 显示 197/199 次提交来自代理）。这决定了三件事：

1. **不能靠"两个人互相看"**。没有第二个稳定的人类审查者，必须靠**机器门禁 + 结构化自查 + 定期深度审计**三层替代。
2. **代理不会主动怀疑自己的假设**。所以流程强制它**贴证据**（命令、输出、测试名），而不是贴结论。
3. **审查预算有限**。人类时间只能花在机器判断不了的地方：数据语义、授权边界、真实用户路径。

流程的目标不是"卡住提交"，而是**让问题在合并前暴露，且同类问题不重复出现**。

## 2. 角色与职责

| 角色 | 谁担任 | 核心职责 | 禁止行为 |
|---|---|---|---|
| **作者** | 提出变更的人或代理 | 定级、自查、贴证据、按意见返工、维护 PR 描述 | 自审自并；把无法验证的项写成"已验证" |
| **审查者** | 非作者的任意成员（当前为人类负责人，或另开的独立审查代理） | 按标准 §5 选维度审查、给四要素意见、给结论 | 只回 "LGTM" 不写依据；把 S3 当 S1 阻塞 |
| **领域审查者** | 涉及安全/隐私/数据一致性时的第二人 | 走专项清单、判定 S0/S1 | 用"整体看着没问题"代替逐条结论 |
| **合并者** | 仓库负责人 | 核验门禁、裁决定级争议、执行合并、登记豁免 | 在 G0 未绿时合并；口头批准替代 PR 记录 |

**最小可行配置**：C1/C2 由"人类负责人"审；C3/C4 由"人类负责人 + 一个独立审查代理（独立上下文、只看 diff 与 PR 描述）"双审。代理审查不能替代人类对**医疗语义**的判断，但能覆盖清单与红线。

## 3. 流程总览

```
任务立项（任务号 + 影响分析）
        │
        ▼
  ┌──────────────┐
  │ 1. 作者自查   │  PR 模板 12 项 + 本地跑门禁
  └──────┬───────┘
         ▼
  ┌──────────────┐

  └──────┬───────┘

         │ 绿

  ┌──────────────┐   不通过 ──► 4b. 返工（≤2 轮，第 3 轮结对）
```

## 4. 分步执行

### 步骤 0 · 立项（编码前）

必须产出（沿用约束 §2「开始前」）：任务号与需求来源、影响范围、设计简述、测试计划、迁移/回滚方案、安全隐私影响、风险与待确认项、预计修改文件清单。

**没有任务号的 PR 直接关闭**，不进入审查。这是防止"顺手改"和"大杂烩提交"的第一道闸。

### 步骤 1 · 作者自查

打开 `.github/pull_request_template.md` 逐项填写。关键要求：

- **每条勾选必须有证据**。写"已测试"无效，要写 `pnpm --filter @ibd/api smoke:parse-source` → PASS，或 `flutter test test/xxx_test.dart` → 12 passed。
- **写清"没做什么"**。无法验证的项标 `BLOCKED` + 原因 + 后续验证方式。
- **自评 diff 规模**。超过 400 行有效改动，先拆。

### 步骤 2 · 提 PR

PR 描述必须包含：变更定级、行为变化（用户能感知到什么不同）、回滚方式、证据区、自查清单。

**PR 规模规则**：

| 有效 diff 行数 | 处理 |
|---|---|
| ≤400 | 正常审查 |
| 400–800 | 允许，但审查者需分两轮看，作者需在描述中给出阅读顺序 |
| >800 | **必须拆分**。例外：数据库迁移、生成物（`*.g.dart`、`schema.d.ts`）、lock 文件、纯删除 |

> 拆分不是为了形式。单次审查超过 60 分钟，发现率断崖下降——这是审查机制失效最常见的原因，比"没人审"更隐蔽。

### 步骤 3 · G0 机器门禁

CI 必须全绿。**红灯期间作者自行修复，不计入审查轮次，也不占用审查者时间。**

当前 CI 覆盖：API build/typecheck、6 个 API smoke、Python 2 个单测、Flutter analyze + 全量 test、依赖审计。
**已知缺口**（标准 §7 已列）：TS 无 lint、PR 不跑 fullstack E2E、无敏感信息扫描。缺口补齐前，由审查者在人工审查中**显式代偿**这几项，并在 PR 中注明"人工代偿 G0 缺口：xxx"。

### 步骤 4 · 人工审查

**时间盒**：首次响应 ≤1 个工作日；单次审查 ≤60 分钟；超时则拆 PR，不硬撑。

**审查顺序**（不要一上来逐行读）：

1. 读 PR 描述 → 是否说清了"改了什么、为什么、怎么验证"。
2. 看 diff 的**文件分布** → 是否跨了不该跨的模块（跨 3 个以上模块的 PR 通常是定级错误或该拆分）。
3. 看**测试改动** → 有没有测试？测的是行为还是实现？断言是否具体？
4. 按标准 §5 选维度，重点看**失败路径**与**边界**。
5. 过一遍标准 §6 红线清单（13 条，1 分钟能过完）。
6. 给结论 + 四要素意见（标准 §10）。

**意见分级使用**：`must`（S0/S1，不修不合）/ `should`（S2，本次修或开 issue）/ `nit`（S3，可忽略）/ `question`（需解释）/ `praise`（至少一条）。

### 步骤 4b · 返工

- 第 1 轮 `Request changes`：作者逐条回应（接受并修 / 不接受并给理由）。
- 第 2 轮：仍不通过 → 升级为**结对审查**（审查者与作者同步过一遍，30 分钟），而不是继续异步往返。
- **禁止**在返工中扩大改动范围。发现新问题 → 新 PR。

### 步骤 5 · 专项审查（C3/C4）

按标准 §5.1–§5.5 + §5.8 逐条给结论，三选一：`通过` / `不适用（原因）` / `不通过`。

**任何"不通过"不得以"后续补"合并**，唯一例外是 hotfix 通道（标准 §8）。

### 步骤 6 · 合并

- 合并方式：squash merge，保留单一语义提交。
- 提交信息：`<任务号>: <动词> <对象>`（如 `T6.2: 修复注射排期重复插入`）。
- 合并后：更新 `docs/session-worklist.md` 状态；S2 意见登记为待办。
- 合并者负责**最后一道确认**：G0 绿、审查结论存在、豁免已记录。三者缺一不合并。

### 步骤 7 · 归档与复盘

**单次**：C3/C4 的专项清单结论随 PR 归档（PR 评论即可，无需另建文件）。

**月度**（每月首个工作日，30 分钟）：

1. 统计标准 §9 的五个指标。
2. 列出本月**逃逸缺陷**（合并后才发现的问题）→ 每条追问：哪道门禁本该拦住？补门禁，而不是补"下次注意"。
3. 列出**红线复发**（§6 中重复出现的模式）→ 复发说明执行问题；连续两月复发 → 升级为 CI 规则或 lint 规则，从"靠人记"改为"靠机器拦"。
4. 输出 `docs/code-review-YYYY-MM.md`，与 2026-10-29 报告同目录、同格式。

**深度审计**：每季度一次全量审计（照 2026-10-29 的方法：分区域并行 + 交叉复核 + 可执行验证），因为日常审查只能看 diff，看不到"跨模块的系统性裂痕"。

## 5. AI 编码代理特别规则

代理产出是本仓库的主要代码来源，以下规则针对其失效模式：

| # | 规则 | 原因 |
|---|---|---|
| A1 | **禁止自审自并**。代理不得批准自己提交的 PR，也不得在无人审查的情况下直接推 main | 代理无法发现自己的假设错误 |
| A2 | **证据优先于结论**。必须贴命令与原始输出，不得写"已验证通过" | 历史出现过"声称通过但未运行" |
| A3 | **一次只碰一个模块**。跨模块变更必须拆成多个 PR 并说明依赖顺序 | 跨模块 PR 的审查发现率最低 |
| A4 | **无法验证必须标 BLOCKED**。真机、凭据、法务相关一律不猜 | 约束 §1.5 |
| A5 | **改动点 → 测试映射**。每个行为变更列出对应测试名；没有测试的必须说明为什么 | 迫使代理显式承认覆盖缺口 |
| A6 | **禁止顺手重构**。发现无关问题只记录，不在本 PR 修 | 约束 §1.9 |
| A7 | **必须引用任务号与 PRD 条目**。无来源的改动不做 | 约束 §1.1 |

审查者对代理产出的 PR 应**默认怀疑"测试是否真实覆盖"与"字段来源是否可信"**，这两类是本仓库历史缺陷的高发区。

## 6. 冲突与升级

| 情形 | 处理 |
|---|---|
| 作者与审查者对定级有分歧 | 合并者裁决，结论写 PR 评论；裁决后不再争论 |
| 审查者要求超出任务范围 | 作者可拒绝，引用约束 §1.9；超范围项转新任务 |
| 需求本身不明确 / 与 PRD 冲突 | **暂停**，按约束 §9 询问，不得自行决定 |
| 无法运行测试且无替代验证 | 标 `BLOCKED`，不合并（约束 §3.3） |
| 紧急线上故障 | 走 hotfix 通道（标准 §8），事后 24h 内补审 |

## 7. 落地路线图（先机器，后人工）

审查机制最容易失败的方式是"一次性上全套流程"，然后两周内荒废。按下列顺序推进，每步都可独立生效：

**第 1 周 · 止血（零成本，立即生效）— ✅ 已完成（T8.1 / T8.4）**
- ✅ 启用 PR 模板（`.github/pull_request_template.md`）。
- ✅ 硬规则 1 可执行化：`pr-guard.yml` + `scripts/pr-guard.mjs`（任务号 / 描述章节 / 定级 / 勾选数 / 证据区）。
- ✅ 定级规则与红线清单（标准 §6）已写入 PR 模板，审查时对照。
- ⬜ 硬规则 2 需管理员开启分支保护：见 [branch-protection.md](branch-protection.md)。

**第 2–3 周 · 补机器门禁（把人工代偿变成自动拦截）— ✅ 已完成（T8.2 / T8.3）**
- ✅ ESLint 9（扁平配置）+ Prettier 3 + `.editorconfig`；`pnpm lint` 0 error（存量 17 项基线化）。
- ✅ CI typecheck 扩到全 workspace；`api-client` / `ui-tokens` 缺 tsconfig 的问题登记为 T8.6。
- ✅ fullstack E2E 改为 PR 触发（带 paths 过滤）。
- ✅ 敏感信息扫描 `scripts/scan-secrets.mjs`（全仓 0 误报，正向检出已验证）。

**第 4 周 · 跑通一轮完整流程**
- 选 3 个真实变更走完 G0–G3，记录卡点。
- 按卡点调整时间盒与分级标准（标准是活的，但修改要走独立任务）。

**第 2 个月起 · 常态化**
- 月度复盘 + 指标统计。
- 红线连续复发 → 升级为 lint 规则或 CI 检查。
- 每季度一次全量深度审计。

## 8. 检查流程本身是否有效（每季度自问）

1. 过去一季度有没有 S0 逃逸？→ 有，则某道门禁失效，定位并补。
2. 有没有 PR 因为"太大"而审查流于形式？→ 有，则规模规则未执行。
3. 有没有红线问题第二次出现？→ 有，则它应该已经变成机器规则。
4. 审查者是否只在挑风格？→ 是，则维度选择错了，回到标准 §5。
5. 作者是否在"猜审查者想要什么"而不是"证明自己是对的"？→ 是，则证据要求没落地。

**流程失效的信号**：PR 描述越来越短、证据越来越少、`LGTM` 越来越多。出现任一信号，立即回到步骤 1 重新收紧，而不是等到下次事故。
